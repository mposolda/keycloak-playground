Credential Proofs & Attestations

OID4VCI · SD-JWT VC · Key Binding

This deck walks through three progressive levels of proof assurance when issuing a Verifiable Credential (VC) over the OID4VCI protocol using the SD-JWT VC format:

Part 1

No Proof

Credential request carries no proof. Issuer cannot bind the credential to a key. Verifier has no holder binding to verify.

Part 2

JWT Proof (no attestation)

Wallet generates a key pair and proves possession in the credential request. Issuer binds the credential to that key. Verifier can verify holder binding.

Part 3

Attested Proof

An Attester (trusted third party) countersigns the proof key, providing the Issuer with additional assurance that the key lives in a trusted device or environment. Issuer validates both the proof and the attestation before issuing.

SD-JWT VC Structure

An SD-JWT Verifiable Credential is a compact string of the form:

<Issuer-signed JWT> ~ <Disclosure 1> ~ <Disclosure 2> ~ ... ~ [<Key-Binding JWT>]

The trailing ~ (no key-binding) or the optional Key-Binding JWT distinguishes presentations with and without holder binding.

PartContentSigned byPurpose
Issuer-signed JWT Header · Payload · Signature

Payload contains: iss, sub, vct, iat, exp,
digest map (_sd), cnf (if key-bound)		 Issuer (Keycloak) Credential authenticity; binds public key of holder when cnf present
Disclosures Base64url-encoded JSON arrays:
[salt, claim_name, claim_value]		 N/A (integrity guaranteed by digest in JWT) Selective disclosure — holder chooses which to reveal
Key-Binding JWT (optional) Header (typ: kb+jwt) · Payload (nonce, aud, iat, sd_hash) · Signature Holder / Wallet (proof key) Proves the presenter holds the private key matching cnf in the VC
Key insight: the cnf claim in the Issuer-signed JWT is what makes a credential key-bound. Without it (Part 1), no holder-binding is possible regardless of what the wallet does at presentation time.

Slide 5 / 11
Part 1

Verifiable Credential Without Proof

What happens

  • Wallet sends credential request without a proofs parameter
  • Issuer issues the credential but has no key to bind — no cnf claim in SD-JWT payload
  • Credential is bearer: anyone who holds it can present it
  • Presentation ends with ~ — no Key-Binding JWT appended

Verifier's view

  • Verifies Issuer's signature on the SD-JWT ✓
  • Checks disclosed claims against digests ✓
  • Cannot verify holder key binding — no cnf exists ✗
  • Cannot distinguish the presenter from anyone else who stole the credential
Risk: credential can be replayed or transferred to a different party.
Slide 6 / 11
Part 2

Verifiable Credential with JWT Proof (No Attestation)

What happens

  • Wallet generates a key pair before credential request
  • Wallet fetches c_nonce from Issuer's nonce endpoint
  • Wallet signs a openid4vci-proof+jwt with the private proof key; the JWT header carries the public proof key inline (jwk)
  • Issuer validates the proof JWT signature, extracts the public key, and embeds it as cnf.jwk in the issued SD-JWT
  • At presentation time, Wallet appends a Key-Binding JWT (signed with private proof key) to the SD-JWT

Verifier's view

  • Verifies Issuer's signature ✓
  • Extracts cnf.jwk from SD-JWT payload
  • Verifies Key-Binding JWT signature against cnf.jwk ✓
  • Verifies nonce, aud, and sd_hash in Key-Binding JWT ✓
Benefit: Proof that the presenter is the same entity that obtained the credential. Prevents bearer/replay attacks.
Slide 7 / 11
Part 3

Verifiable Credential with Attested Proof

What happens (extra steps vs Part 2)

  • Wallet sends its public proof key to the Attester
  • Attester checks the key is in a trusted environment (e.g. hardware-backed), then issues a key-attestation JWT wrapping the proof public key, signed by the attestation private key
  • Wallet embeds the key-attestation JWT in the credential-request proof (either as proofs.attestation or as key_attestation header on the proof JWT)
  • Issuer verifies both the proof JWT and the attestation JWT against the Attester's public key (registered in the Trusted Key IDP)

Keycloak configuration

  • Generate attestation key pair in fapi-playground
  • Create a Trusted Key IDP in Keycloak admin console; paste the attestation public JWKS
  • Link the Trusted Key IDP to the OIDC client under OpenID for Verifiable Credentials → Trusted Key providers
  • Enable Cryptographic binding required on the credential client scope; add attestation to Supported proof types

Demo Walkthrough — fapi-playground + Keycloak

Part 1

No Proof

  1. Set OID4VCI proof type = none
  2. Click Credential request
  3. Observe: proofs absent in request body
  4. Observe: SD-JWT has no cnf claim
  5. Presentation ends with ~
Part 2

JWT Proof

  1. Enable Cryptographic binding required on credential scope; add jwt proof type
  2. Click Generate proof key
  3. Set OID4VCI proof type = jwt
  4. Click Credential request
  5. Click Show last verifiable credential — see cnf in payload
  6. Create presentation — Key-Binding JWT is appended
Part 3

Attested Proof

  1. Complete Part 2 setup (proof key + jwt in Supported proof types)
  2. Also add attestation to Supported proof types on credential scope
  3. Click Generate attestation key — copy JWKS shown
  4. In Keycloak admin: Identity Providers → create Trusted Key IDP, paste JWKS
  5. On OIDC client → Advanced → OpenID for Verifiable Credentials → Trusted Key providers → add IDP
  6. Set OID4VCI proof type = attestation
  7. Click Credential request — observe proofs.attestation in request body
  8. SD-JWT still carries cnf; Verifier sees identical holder binding as in Part 2

Key Takeaways

Proof serves two purposes

  • Anti-replay: the c_nonce in the proof prevents a captured credential request from being replayed
  • Key binding: the public proof key embedded in the SD-JWT ties the credential to the Wallet's key pair

Attestation adds a third guarantee

  • The Attester vouches that the proof key lives in a trusted environment (e.g. hardware secure element)
  • This is issuance-time assurance — not visible in the issued SD-JWT unless the Issuer explicitly adds claims

Issuer responsibilities

  • Configure credential scope to require proofs (Cryptographic binding required)
  • Register Attester's public key via Trusted Key IDP (for Part 3)
  • Link the IDP to the client (Trusted Key providers)

Relevant specifications

  • OID4VCI spec — §8.2 Proof Types
  • SD-JWT draft — §4.3 Key Binding
  • SD-JWT VC draft
  • Keycloak docs — OID4VCI proofs
Bottom line: Use no proof only for low-assurance or legacy scenarios. Use JWT proof for standard holder-binding. Add attestation when the Issuer needs to trust the security properties of the Wallet's key storage (e.g. regulated sectors, high-assurance identity).
